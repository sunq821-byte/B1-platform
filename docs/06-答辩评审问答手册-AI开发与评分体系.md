## 1. 文档说明

### 1.1 编写目的

本项目采用 **AI Native Development（Vibe Coding）** 模式完成设计与实现：开发过程中使用 DeepSeek、Codex、Claude、Cursor Agent、Composer 2.5 等工具辅助编码；产品本身则内置 **AI 辅助评分引擎**，对学生实践成果进行结构化分析。

评委和学院老师可能从两个方向提问：

| 提问方向 | 典型关切 |
|----------|----------|
| **开发方法论** | 「你们是不是让 AI 写代码？质量怎么保证？」 |
| **产品 AI 评分** | 「AI 打分准不准？会不会替代教师？有没有合规风险？」 |

本文档将上述两类问题所需的**事实依据、约束词原文、设计决策**集中整理，便于答辩前快速查阅与口头应答。

### 1.2 使用方式

- **答辩前**：通读 Part C 问答库，重点记忆「一句话应答」
- **被追问细节时**：引用 Part A / Part B 中的约束编号或 Prompt 原文
- **需要演示时**：打开学生端 AI 结果页，指出界面免责声明与四维度报告

### 1.3 文档边界

- ✅ 完整收录：产品 PRD 约束、PromptBuilder 运行时 Prompt 全文、CLAUDE.md 开发宪法
- ✅ 如实说明：Vibe Coding 工具分工与文档驱动流程
- ❌ 不包含：Cursor 历史会话原文（未入库，无法逐字还原）
- ❌ 不涉及：代码修改建议（本文档仅描述现状）

## 2. 核心概念：双层 AI 体系

```
┌──────────────────────────────────────────────────────────────┐
│                    第一层：开发侧 AI                           │
│  用途：辅助团队写代码、写文档、做架构决策                        │
│  工具：DeepSeek v4 Pro / Composer2.5 / Codex / Claude / Cursor│
│  约束：CLAUDE.md + PRD + Design System + API Contract         │
│  产出：源代码、数据库迁移、产品文档                              │
└──────────────────────────┬───────────────────────────────────┘
                           │ 构建
                           ▼
┌──────────────────────────────────────────────────────────────┐
│                    第二层：运行时 AI                           │
│  用途：对学生提交的成果进行辅助分析与参考评分                    │
│  模型：DeepSeek-Chat（代码/文本）+ Qwen-VL-Max（截图/UI）       │
│  约束：AI-01~06 产品原则 + PromptBuilder 三层 Prompt           │
│  产出：结构化诊断报告 + AI 参考分（非最终成绩）                  │
└──────────────────────────────────────────────────────────────┘
```

**关键区分（答辩必答）：**

> 开发时 AI 是**工程师的工具**；运行时 AI 是**产品的功能**。两者约束词不同、目标不同、责任边界不同。产品内的 AI 评分始终处于「人在回路（Human-in-the-Loop）」之下，教师拥有最终决策权。

## 3. Part A — Vibe Coding 开发侧 AI 提示词体系

### 3.1 项目宪法：CLAUDE.md 核心约束

项目根目录 `CLAUDE.md` 是所有开发 AI 助手的**最高优先级持久规则**，从项目之初即确立：

#### 3.1.1 项目定位约束

| 约束词 | 含义 |
|--------|------|
| 企业级、非 Demo | 每次决策前自问：放到生产环境是否合格 |
| 真实商业价值 | 目标：软件杯竞赛 + 后续产品化 + 软著 |
| AI Native Development | 开发模式声明，但不降低质量标准 |

#### 3.1.2 五条开发原则

| 编号 | 原则 | 约束词 |
|------|------|--------|
| P-01 | MVP First | 先最小可运行产品，非 MVP 功能推迟 |
| P-02 | Component First | 优先抽象可复用组件，页面由组件组合，**禁止复制 UI 代码** |
| P-03 | Design First | 先规范/设计，后代码。**禁止跳过设计直接写代码** |
| P-04 | Simplicity First | 保持设计、代码、交互简单，不为复杂而复杂 |
| P-05 | Specification First | PRD → Design System → API Contract → Develop |

#### 3.1.3 代码规范约束

```
- Composition API + <script setup> + TypeScript
- 业务逻辑 → Composable，状态 → Pinia，接口 → Axios
- Vue 组件超过 300 行必须拆分
- 禁止：Options API、Vue2 写法、hardcode、魔法数字、超长函数
- 遵循：高内聚低耦合 / SOLID / KISS / DRY / YAGNI
```

#### 3.1.4 UI 规范约束

| 变量 | 值 | 用途 |
|------|-----|------|
| Primary | `#1677FF` | 主按钮、链接、选中 |
| Success | `#00B96B` | 状态绿（不作主按钮） |
| Navy | `#0B3A5C` | Logo/稳重标题 |
| AI | `#722ED1` | AI 建议/置信度专属 |
| Background | `#F5F7FA` | 页面背景 |

**禁止项：** 玻璃拟态、炫酷动画、复杂渐变、颜色污染、侧边栏导航（采用顶部导航）

#### 3.1.5 产品级 AI 规则（开发时即写入宪法）

| 约束 | 说明 |
|------|------|
| AI 只能 | 分析、建议、解释、提供评分依据 |
| AI 输出必须 | 可解释、可追溯、可复核 |
| **禁止** | AI 直接输出最终成绩 |
| 最终决策权 | 在教师 |

> 答辩要点：产品「AI 不替代教师」的原则，从开发阶段就已写入项目宪法，不是事后补丁。

#### 3.1.6 Git Commit 规范

```
feat: / fix: / docs: / style: / refactor: / perf: / test: / build: / chore:
禁止：update、modify、123、aaa 等无意义 message
```

## 4. Part B — 系统运行时 AI 评分约束词

### 4.1 产品层硬约束（PRD AI-01 ~ AI-06）

| 编号 | 原则 | 完整说明 | 系统落地 |
|------|------|----------|----------|
| **AI-01** | AI 仅提供建议 | 系统**禁止**将 AI 输出直接作为最终成绩发布 | 成绩发布须经教师 `TeacherReview` 确认 |
| **AI-02** | 人工拥有最终决定权 | 所有成绩发布须经教师或授权导师确认 | 教师可覆盖 AI 评分并填写覆盖原因 |
| **AI-03** | 结果可解释 | 每条 AI 建议须附带依据、维度归属及置信度 | `AiAnalysisDetail` 存 reason/suggestion/confidence |
| **AI-04** | 结果可追溯 | 保留 AI 原始输出、人工修改记录及发布时间 | `AiAnalysis.rawResponse` + 审计日志 |
| **AI-05** | 分层分析降幻觉 | 确定性规则优先，LLM 用于语义层分析 | L1 文件校验 → L2 静态分析 → L3 LLM |
| **AI-06** | AI 参考分非最终成绩 | `overall_score` 仅作 AI 参考分展示 | 界面多处明示免责声明 |

### 4.2 业务流程约束（与评分强相关）

#### 4.2.1 试交 + 确认提交（方案 A）

```
学生试交 → AI 异步分析 → 生成 AI 参考分 → 学生确认提交 → 教师复核 → 成绩发布
     ↑                                              │
     └── 不满意且未达 AI 次数上限，可重新试交 ────────┘
```

| 编号 | 约束 | 说明 |
|------|------|------|
| SUB-01 | 试交阶段教师不可见 | 教师端**不得**查看试交成果、AI 报告及 AI 参考分 |
| SUB-03 | AI 次数可配 | 每任务 `max_ai_analyze_count` 默认 **3 次**，教师可配置 |
| SUB-04 | 次数用尽仍可提交 | AI 次数用尽后，学生**仍须**能基于最后一次试交确认提交 |
| SUB-06 | 驳回重置次数 | 教师驳回重提后，AI 分析次数**重置**为任务配置值 |
| SUB-08 | 界面明示 | 必须显示「仅供参考，非最终成绩；最终成绩以教师评定为准」 |

#### 4.2.2 提交状态机（评分相关状态）

| 状态 | 代码 | 教师可见 | 含 AI 参考分 |
|------|------|----------|--------------|
| 草稿试交 | `DRAFT` | 否 | 待分析 |
| AI 分析中 | `ANALYZING` | 否 | 分析中 |
| 待学生确认 | `AI_READY` | 否 | **是** |
| 已确认待审 | `SUBMITTED` | **是** | 是（参考） |
| 已发布成绩 | `GRADED` | 是 | 教师最终分 |

#### 4.2.3 失败处理约束

| 场景 | 系统行为 | 约束意图 |
|------|----------|----------|
| 全部 Provider 调用失败 | 状态 `FAILED`，提示「AI 服务暂时不可用，请稍后重试」 | **禁止伪造 0 分 COMPLETED** |
| Provider 单次失败 | 记录 warn 日志，继续处理其他文件 | 部分成功仍可用 |
| API 超时/5xx | 自动重试（默认最多 3 次） | FR-06-09 |

### 4.3 评价框架：四维度 + R/S/R/O

#### 4.3.1 系统固定四维度基线

依据 ADR-012 与 PRD FR-04，全平台统一四维度（V10 迁移后通用名称）：

| 维度 | 通用含义 | 跨专业示例 |
|------|----------|------------|
| **完成度** | 任务要求达成程度 | 实验步骤完成、功能实现、方案落地 |
| **规范性** | 格式、流程、规范遵循 | 引用格式、代码规范、设计规范 |
| **质量** | 成果本身质量 | 论证深度、代码质量、设计美感 |
| **表达与完整性** | 呈现与文档完整程度 | 报告结构、图表齐全、说明清晰 |

> 数据库 `evaluation_standard` id=1000 存储系统默认标准；所有实训任务默认引用此基线。维度权重与满分由系统配置，教师当前版本**不可自定义权重**（个性化通过 R/S/R 文本细则实现）。

#### 4.3.2 任务级 R/S/R/O 分工

| 段 | 名称 | 填写者 | 作用 |
|----|------|--------|------|
| **R** | Role · 角色 | 教师 | 定义 AI 评审时的角色定位（如「资深 Java Web 阅卷教师」） |
| **S** | Skill · 能力要求 | 教师 | 描述应重点检查的能力要点 |
| **R** | Rule · 打分细则 | 教师 | **重点**：具体扣分标准、分值规则 |
| **O** | Output · 输出格式 | **系统固定** | 标准四维度 JSON，教师不可修改 |

前端 `GradingRuleForm.vue` 提示：

> 「评分细则（用于 AI 评审，可留空使用系统默认四维度）」  
> 「Output Format · 输出格式：系统已固定为标准四维度 JSON，无需填写」

教师填写的前三段在提交时组装为 `grading_rule` 长文本：

```
Role：{roleText}
Skill：{skillText}
Rule：{ruleText}
```

#### 4.3.3 评分细则样例（图书管理系统）

```markdown
## 完成度 (Completion)
- **R**：必须实现图书 CRUD、借阅记录、登录接口
- **S**：借阅状态流转正确，边界条件有处理
- **R/O**：缺核心接口扣 5～15 分；仅演示无持久化扣 10 分

## 规范性 (Standard)
- **R**：分层包结构、统一响应体、Git 提交规范
- **S**：命名、注释、异常处理符合课程规范
- **R/O**：无分层扣 8 分；无 README 扣 3 分

## 质量 (Quality)
- **R**：无严重逻辑错误，SQL 无注入风险
- **S**：事务、并发考虑合理
- **R/O**：N+1 查询扣 5 分

## 表达与完整性 (Expression)
- **R**：实训报告含功能说明、截图、运行步骤
- **S**：结构清晰，问题与改进计划完整
- **R/O**：缺报告扣 15 分
```

### 4.4 Prompt 三层架构

运行时 Prompt 由 `PromptBuilder.java` 构建，分三层注入：

```
┌─────────────────────────────────────────────────┐
│ Layer 1 · System Prompt（系统固定模板）           │
│   角色定义 + 评审规则 + 扣分映射 + JSON 输出约束   │
├─────────────────────────────────────────────────┤
│ Layer 2 · 四维度基线（从 DB 动态注入）            │
│   维度名 + 权重 + 满分 + 描述                    │
├─────────────────────────────────────────────────┤
│ Layer 3 · 任务级细则（教师 grading_rule 原文）    │
│   「本任务特定评分细则(教师指定)」               │
└─────────────────────────────────────────────────┘
          ↓ 合并为 system message
┌─────────────────────────────────────────────────┐
│ User Prompt（按文件类型分支）                     │
│   代码类：任务描述 + 文件名 + 代码内容            │
│   截图类：任务描述 + UI 五维检查清单              │
└─────────────────────────────────────────────────┘
          ↓
    DeepSeek-Chat / Qwen-VL-Max
    temperature = 0.1, max_tokens = 4096
```

**Provider 路由规则：**

| 文件类型 | Provider | 模型 |
|----------|----------|------|
| 代码文件（.java/.py/.vue/.ts 等） | DeepSeek | deepseek-chat |
| 图片文件（.png/.jpg 等） | Qwen | qwen-vl-max |

### 4.5 System Prompt 全文（Layer 1 + 2 + 3 模板）

以下为 `PromptBuilder.buildSystemPrompt()` 生成的 System Prompt 结构。**{dimensions}** 和 **{gradingRule}** 为运行时动态替换。

```text
你是一个专业的软件实训代码评审专家。你需要根据给定的评价维度，对学生的代码进行严格、公正的评审。

## 评审规则
1. 严格按照评价维度的定义逐项检查代码
2. 每个发现的问题必须包含：维度名称、问题类型、严重程度(CRITICAL/MAJOR/MINOR/INFO)、建议扣分、详细原因、改进建议
3. 扣分建议：CRITICAL扣对应维度满分的50-100%，MAJOR扣20-50%，MINOR扣5-20%，INFO扣0-5%
4. 最终总分 = 100 - 各维度扣分加权合计
5. 同时指出代码的优点和不足
6. 给出具体的改进计划

## 评价维度
{dimensions}
{gradingRule}
## 输出格式
必须严格返回以下JSON格式（不要包含任何其他文字）：
{
  "overall_score": <0-100的整数>,
  "summary": "<总体评价，200字以内>",
  "dimensions": [
    {
      "dimension_name": "<维度名称>",
      "dimension_code": "<维度代码>",
      "issue_type": "<CODE_STYLE|LOGIC|PERFORMANCE|SECURITY|DOCUMENTATION|UI_ISSUE>",
      "severity": "<CRITICAL|MAJOR|MINOR|INFO>",
      "suggest_deduct": "<建议扣分>",
      "reason": "<详细原因>",
      "suggestion": "<改进建议>",
      "line_number": <行号或null>,
      "confidence": <0.0-1.0的可信度>
    }
  ],
  "strengths": ["<优点1>", "<优点2>"],
  "weaknesses": ["<不足1>", "<不足2>"],
  "improvement_plan": "<具体改进计划>"
}
```

**{dimensions} 注入示例（四维度基线）：**

```text
1. **完成度** (权重:25, 满分:25): 任务要求达成程度：实验步骤完成、功能实现、方案落地
2. **规范性** (权重:25, 满分:25): 格式、流程、规范遵循：引用格式、代码规范、设计规范
3. **质量** (权重:25, 满分:25): 成果质量：架构设计、算法与性能、可靠性
4. **表达与完整性** (权重:25, 满分:25): 呈现与文档完整程度：报告结构、图表齐全、说明清晰
```

**{gradingRule} 注入示例（教师填写时）：**

```text
## 本任务特定评分细则(教师指定)

Skill：重点检查 Spring Boot 分层、RESTful 规范、SQL 安全
Rule：缺少 Controller 层扣 10 分；SQL 注入风险扣 15 分；无 README 扣 5 分
```

## 5. Part C — 评委与学院老师常见问题应答

### 5.1 关于 AI 开发方法论

---

#### Q1：你们的代码是不是 AI 写的？质量怎么保证？

**一句话应答：** 我们采用 AI Native Development，但用文档规范和检查清单约束 AI 产出，核心架构与产品规则由人决策，AI 是加速器而非决策者。

**展开说明：**

1. **文档先行**：PRD → Design System → API Contract 完成后才开发，AI 不得跳过
2. **项目宪法**：`CLAUDE.md` 明确禁止 Demo 级代码、禁止 hardcode、组件超 300 行必须拆分
3. **人类决策点**：ADR-012 评分融合方案、试交流程方案 A 等关键架构由人确认
4. **可验证**：Flyway 迁移、API Contract、PRD 第 12 章功能自检清单均可独立验收

---

#### Q2：不同 AI 工具会不会导致代码风格混乱？

**一句话应答：** 通过统一的技术栈约束和四套标准会话模板，所有工具输出对齐同一规范。

**展开说明：**

- 前端统一 Vue 3 Composition API + TypeScript
- 后端统一 Spring Boot 3 + MyBatis Plus
- 无论 DeepSeek、Claude 还是 Cursor Agent，Prompt 前缀均指向同一份 CLAUDE.md 和 docs 规格
- Git commit 规范统一为 `feat/fix/docs/...`

---

#### Q3：AI 辅助开发会不会有知识产权或抄袭问题？

**一句话应答：** 本项目为原创产品设计，AI 生成代码在团队规范约束下开发，产品文档、架构决策、数据库设计均为团队独立完成。

**展开说明：**

- 产品需求、四维度评价框架、试交流程为团队原创设计
- 参考 ADR 记录了关键架构决策过程
- 可提交软著材料：`docs/01-PRD` + 源代码 + 本手册

---

#### Q4：为什么选 Vibe Coding 而不是传统开发？

**一句话应答：** 在 MVP 阶段，Vibe Coding 让我们把精力集中在产品设计和业务闭环上，而不是重复性 CRUD；但质量标准不降低。

**展开说明：**

- 2 人小团队要交付企业级全栈产品（前端 + 后端 + AI + 部署）
- AI 加速：页面组件、API 对接、迁移脚本、文档同步
- 人负责：PRD 定义、UI 规范、ADR 决策、联调验收

---

### 5.2 关于 AI 评分准确性

---

#### Q5：AI 打分准不准？能信吗？

**一句话应答：** AI 分是**参考分**，不是最终成绩；系统要求每条扣分有依据和置信度，低置信度必须教师人工评分。

**展开说明：**

1. **AI-06**：`overall_score` 明确标注为 AI 参考分
2. **四维度结构化输出**：不是黑盒一个分数，而是分项问题 + 原因 + 建议
3. **置信度三级**：<60% 强制人工；Design System 有明确交互规范
4. **temperature=0.1**：降低 LLM 随机性
5. **教师可覆盖**：覆盖须填写原因，留痕可追溯

---

#### Q6：AI 会不会误判学生？比如风格差异被扣分？

**一句话应答：** 这正是「人在回路」存在的原因——AI 提供初筛和参考，教师拥有最终决定权，且可逐条采纳或驳回 AI 建议。

**展开说明：**

- 试交流程让学生先看 AI 报告再决定是否提交
- 教师复核页可查看 AI 推理依据（Reason Block 设计）
- 教师覆盖评分组件要求填写覆盖原因
- 企业导师（P1）可参与校企实训的双重复核

---

#### Q7：不同教师标准不一样，AI 怎么统一？

**一句话应答：** 系统固化**四维度通用基线**保证跨任务可比性；教师通过 R/S/R 文本注入任务级个性化细则，两者融合后送入 AI。

**展开说明：**

- 四维度：完成度、规范性、质量、表达与完整性（PRD FR-04-02）
- ADR-012 决策：不用 AI 自由归纳维度（保证雷达图稳定），不用 R/S/R/O 完全取代维度（保证统一框架）
- 教师 Rule 段写具体扣分规则，如「缺 README 扣 3 分」
- 目标：同批次评分方差缩小（PRD G-04）

---

#### Q8：代码和图片评分用的是同一个模型吗？

**一句话应答：** 不是。代码/文本走 DeepSeek-Chat，截图/UI 走 Qwen-VL-Max 多模态模型，通过 Provider 抽象层按文件类型自动路由。

**展开说明：**

- `AiProviderRouter` 按文件扩展名路由
- 图片传 base64 data URI（避免 MinIO 内网 URL 无法被云端 API 访问）
- 多文件提交时逐文件分析，综合加权得 AI 参考分

---

#### Q9：AI 分析失败了怎么办？会不会给学生乱打 0 分？

**一句话应答：** 不会。全部 Provider 失败时状态为 FAILED，提示重试；禁止伪造 0 分 COMPLETED。

**展开说明：**

- `AiServiceImpl` 明确：「Every provider call failed... Degrade honestly」
- 自动重试最多 3 次（FR-06-09）
- AI 次数用尽后仍可基于最后一次试交确认提交（SUB-04）

---

### 5.3 关于教师角色与合规

---

#### Q10：AI 会不会替代教师？教师还有价值吗？

**一句话应答：** 不会替代。AI 是「助教级初筛」，教师是「最终裁判」——这是从 PRD 到 CLAUDE.md 到 UI 文案的三层一致设计。

**展开说明：**

| 角色 | AI 做什么 | 教师做什么 |
|------|-----------|------------|
| 学生试交阶段 | 生成诊断报告 + AI 参考分 | **不可见**（保护学生探索空间） |
| 确认提交后 | 提供结构化建议 | 审阅报告、采纳/驳回建议、确认或覆盖成绩 |
| 低置信度 | 标注「必须人工评分」 | 全量人工复核 |

---

#### Q11：学生试交时教师看不到，会不会有作弊空间？

**一句话应答：** 试交阶段的设计意图是让学生**安全试错**——AI 辅助改进后再正式提交；确认提交后成果锁定，且教师看到的是学生满意后选择的最终版本。

**展开说明：**

- 试交：学生 ↔ AI 的闭环，教师不参与
- 确认提交：每轮仅 1 次，作为任务完成标志
- 截止前未确认 = 未完成，**禁止**系统自动递交末次试交（SUB-09）
- 确认后不可自行修改，仅教师驳回可重提

---

#### Q12：AI 评分有没有合规风险？是否符合教育评价规范？

**一句话应答：** 系统遵循「AI 建议 + 人工确认」原则，符合 GB/T 25000.51 质量评价框架中对可追溯、可复核的要求；AI 参考分与最终成绩严格分离。

**展开说明：**

- PRD 引用 GB/T 25000.51-2016
- AI-01~06 六条原则覆盖：建议性、人工决策、可解释、可追溯、降幻觉、非最终成绩
- 数据库 `ai_analysis` 与 `score_record` 分表存储
- 关键操作有审计日志

---

#### Q13：学生会不会过度依赖 AI 刷分？

**一句话应答：** 每任务 AI 分析默认上限 3 次，且 AI 分不是最终成绩；学生需要的是理解 AI 反馈后改进成果，而非刷出高分。

**展开说明：**

- `max_ai_analyze_count` 教师可配，默认 3
- 试交时间线展示各次 AI 参考分，学生可看到改进轨迹
- 教师 Rule 段可设定严格扣分规则
- 确认提交后锁定，不能无限试交

---

### 5.4 关于技术架构与扩展

---

#### Q14：为什么用 DeepSeek 而不是 GPT-4？

**一句话应答：** 采用 OpenAI Compatible 协议抽象，DeepSeek 为当前默认 Provider；架构上可切换，且 DeepSeek 在代码理解场景性价比更高。（主要是dp便宜）

**展开说明：**

- `AiProvider` 接口 + `AiProviderRouter` 路由
- 配置在 `application-*.yml`，密钥不入库
- 多模态场景用 Qwen-VL（国内 API 稳定）
- 后续可扩展本地模型或自研领域模型（PRD 列为研究方向）

---

#### Q15：四维度对所有专业都适用吗？计算机以外的课程怎么办？

**一句话应答：** 四维度是**通用语义框架**，不是计算机专属；不同专业通过任务描述和 R/S/R 细则注入学科特定评判标准。

**展开说明：**

| 维度 | 管理学报告 | 机械设计 | 软件实训 |
|------|-----------|----------|----------|
| 完成度 | 调研步骤完成 | 方案落地 | 功能实现 |
| 规范性 | 引用格式 | 制图规范 | 代码规范 |
| 质量 | 论证深度 | 设计合理性 | 架构与性能 |
| 表达与完整性 | 报告结构 | 说明书齐全 | README 文档 |

- PRD FR-04-07（P1）：后续支持按专业自定义维度展示名称

---

#### Q16：Prompt 会不会被学生 Prompt 注入攻击？

**一句话应答：** 学生提交的是成果文件（代码/文档/图片），不是 System Prompt；System Prompt 由服务端 `PromptBuilder` 构建，用户不可修改。

**展开说明：**

- System Prompt 完全服务端生成
- 四维度基线从 DB 读取，非用户输入
- `grading_rule` 仅教师可写
- 学生输入的代码内容作为 User Prompt 的一部分，但 JSON 输出格式由 System Prompt 锁定

---

#### Q17：Token 成本怎么控制？

**一句话应答：** 系统记录每次分析的 Token 用量；AI 次数上限默认 3 次；temperature 0.1 减少无效输出；异步执行不阻塞用户。

**展开说明：**

- `ai_analysis.token_input/output/total` 持久化
- 教师可配置 `max_ai_analyze_count`
- 后台线程异步分析（FR 性能要求 C-01）
- 失败重试有上限

---

### 5.5 关于产品与竞品差异

---

#### Q18：和 xx 教学平台 / xx 判题系统相比，你们的差异是什么？

**一句话应答：** 我们不是 OJ 判题系统，而是**跨专业实践教学成果评价平台**——核心是统一四维度 + 任务级细则 + AI 参考分 + 教师复核的完整闭环。

**展开说明：**

| 对比项 | OJ/判题系统 | 衡迹 |
|--------|------------|------|
| 成果类型 |  mainly 代码 | 代码 + 文档 + 设计稿 + ZIP |
| 评价框架 | 通过/不通过 | 四维度 + R/S/R 细则 |
| AI 角色 | 通常无或自动判分 | 参考分 + 人在回路 |
| 流程 | 提交 → 结果 | 试交 → AI → 确认 → 教师复核 |
| 受众 | 计算机专业 | 高校全专业实践教学 |

---

#### Q19：如果 LLM 幻觉产生了不存在的代码问题怎么办？

**一句话应答：** 三层防护——分层分析降幻觉（AI-05）、置信度标注 + 低置信强制人工、教师逐条审阅可驳回。

**展开说明：**

- L1 确定性规则（文件格式/大小）零幻觉
- L2 静态分析（代码规范）零幻觉
- L3 LLM 语义分析须人工复核
- 每条问题有 `confidence` 字段
- 原始 JSON 保存在 `raw_response` 供事后审计

**一句话应答：** 当前通过 Prompt 工程 + 四维度框架 + 教师细则实现可配置评价；自研领域模型列为 PRD 后续研究方向，不在 MVP 范围。

**展开说明：**

- MVP：DeepSeek + Qwen API + PromptBuilder
- P1：按专业/学院自定义维度模板（FR-04-07）
- 远期：领域微调模型，但始终保留 Human-in-the-Loop
- ADR 机制保证架构演进有记录

### 附录 B — ADR-012 决策摘要

**问题：** 原标准管理页操作割裂，不符合大模型结构化 Prompt 的工作方式。

**决策：**

1. 删除教师端标准管理页
2. 四维度下沉为系统固定基线
3. 教师在建任务时填写 Role/Skill/Rule 三段文本
4. Output Format 由系统固定 JSON
5. `PromptBuilder` 将四维度 + 教师细则融合注入 AI

**未采纳方案：**

- R/S/R/O 完全取代维度 → 丢失统一框架
- AI 自行归纳维度 → 雷达图不稳定
- 双模式切换 → 违反 KISS
