# 产品需求说明书

## 基于大模型的软件实训教学检查评价与报表系统

---

# 1 引言

## 1.1 编写目的

本文档旨在明确基于大模型的软件实训教学检查评价与报表系统的功能边界、业务规则与非功能指标，作为项目全生命周期开发、测试、验收的统一基准，供项目开发组、测试组及竞赛评审参照执行。后续所有需求分析、设计、开发与测试工作均以此文档为准，任何需求变更均须通过正式变更流程记录并审批，不得随意更改。

## 1.2 项目背景

当前职业教育机构及高校校企合作项目中，普遍存在软件实训成果评估效率低、标准不统一的痛点。企业内训或实训基地需批量审核学员代码、项目文档，传统人工方式耗时久、主观偏差大，且难以快速形成数据化评估报告供复盘优化；高校与企业协同实训时，也需一套兼顾教学要求与企业标准的评价工具，打通实训成果与岗位需求的衔接。

全国开设软件工程、计算机科学与技术等相关专业的本科院校超过900所、职业院校超过1400所，年均参与软件实训的学生规模超过200万人。大多数院校的实训评价仍依赖人工线下模式：教师需逐份下载、解压、核对代码成果与实训报告，大班教学下单次批改周期往往超过一周；不同教师评分尺度不一致，主观偏差大；学生错误与能力薄弱点无法量化沉淀，教学缺乏数据支撑；成绩统计依赖人工整理，不满足归档要求。企业侧同样面临类似困境：新员工入职培训、项目实训基地的成果审核缺少统一评价标准与自动化工具，难以高效量化培训效果。

教育部《教育信息化2.0行动计划》明确提出以人工智能、大数据等新技术驱动教学模式变革，《职业教育提质培优行动计划（2020-2023年）》要求强化实践教学环节并提升实训教学质量监控能力。基于此，本赛题聚焦"高校-企业协同实训"核心场景，打造智能化实训评价系统，面向授课教师、实训学生、企业导师、教研负责人及系统管理员等多类用户，实现"课程管理→实训发布→标准配置→成果提交→智能分析→教师审核→能力成长→教学复盘"的完整业务闭环。

# 2 总体描述

## 2.1 产品目标与范围

**产品愿景**：聚焦"高校-企业协同实训"核心场景，打造面向职业教育机构、高校及企业的智能化实训管理与评价平台。以软件工程全生命周期为主线、AI 分析能力为辅，打通实训成果与岗位需求的衔接，实现实训评价的标准化、自动化与数据化。

**建设目标**：
- 实现课程管理、实训发布、成果提交、AI 智能分析、教师/导师审核、报表生成的完整业务闭环；
- 将教师及企业导师批改工作量降低 60% 以上，单次实训批改周期从平均 7 天降至 2 天以内；
- 建立覆盖代码规范、功能完成度、设计质量、文档完整性四个维度的标准化评价体系，兼顾教学要求与企业用人标准，同批次评分方差缩小 50% 以上；
- 实现学情数据与培训效果可视化，支撑教研团队及企业培训部门基于数据的课程持续优化与人才选拔。

**适用范围**：高校授课教师、实训学生、企业导师、教研负责人、企业培训管理员、系统管理员。

**排除范围**：不包含在线课程视频播放、学分学籍管理系统对接、在线支付与收费、第三方教学平台（如超星、智慧树）深度集成。

## 2.2 运行环境约束

**服务端环境**：
- CPU：4 核及以上
- 内存：16 GB 及以上
- 操作系统：Linux（Ubuntu 20.04+ 或 CentOS 7+）
- 数据库：MySQL 8.0+
- 运行时：Node.js 18+、Python 3.10+
- 容器化：Docker 20.10+

**客户端环境**：
- 浏览器：Chrome 90+、Edge 90+、Firefox 88+
- 分辨率：1920×1080 及以上
- 网络：校园内网环境，带宽 ≥ 100 Mbps

## 3.2 详细功能需求

### 3.2.1 用户认证与权限管理（P0）

- 系统必须支持学生、教师、教研负责人、系统管理员四种角色注册与登录；
- 登录方式必须支持账号密码登录，应支持学号/工号一键登录；
- 系统必须基于 RBAC 模型实现角色权限隔离，不同角色登录后呈现独立路由与功能菜单；
- 系统必须对每次请求进行 JWT 令牌校验，令牌过期后自动跳转登录页；
- 密码必须采用加盐哈希（bcrypt/argon2）存储，禁止明文存储。

### 3.2.2 课程管理（P0）

- 教师必须能够创建课程，填写课程名称、课程编号、学期、授课班级等信息；
- 教师必须能够将课程与授课班级（学生群体）关联，支持从学生库批量导入；
- 教师应能够编辑课程基本信息、归档已完成课程；
- 学生必须能够查看自己所选课程的列表及课程基本信息。

### 3.2.3 实训任务管理（P0）

- 教师必须能够创建实训任务，配置任务名称、描述、截止时间、提交方式（ZIP / Git）；
- 教师必须能够配置重复提交策略（覆盖 / 仅首次有效 / 截止前最后一次）；
- 教师必须能够发布实训任务，发布后学生端可见；
- 教师应能够查看学生提交状态（未提交 / 已提交 / 逾期提交），支持批量催交提醒；
- 学生必须能够查看实训任务详情并在截止时间前提交成果。

### 3.2.4 评分标准配置（P0）

- 系统必须固化四维评价框架：代码规范（权重 25%）、功能完成度（权重 35%）、设计质量（权重 25%）、文档完整性（权重 15%）；
- 教师必须能够针对每个实训任务自定义评分细则（R/S/R 准则），指定每个维度的具体检查项与扣分规则；
- AI 评分时，系统必须将固定框架与任务级自定义细则融合计算，生成可追溯的诊断报告；
- 系统必须支持评分标准模板的保存与复用。

### 3.2.5 成果提交（P0）

- 学生必须能够通过 ZIP 文件上传方式提交实训成果；
- 学生必须能够通过填写 Git 仓库地址方式提交实训成果；
- 系统必须对上传文件进行格式与大小校验（ZIP 最大 500 MB）；
- 系统必须记录提交时间戳，超时提交标记为"逾期"并单独标注；
- 学生应能够在截止时间前重新提交（根据教师配置的策略处理）。

### 3.2.6 AI 代码分析（P0）

- 系统必须自动对提交的代码进行静态分析，覆盖规范检查（命名、注释、格式）、逻辑缺陷检测（空指针、资源泄露、边界条件）和功能完整度评估；
- 分析结果必须以诊断报告形式呈现，每个扣分项必须标注具体文件路径、行号、问题类型、扣分依据；
- 系统应支持 Code Agent 进行深度语义分析；
- 分析完成后，系统必须自动生成总评分建议供教师审核。

### 3.2.7 AI 文档分析（P0）

- 系统必须自动对提交的实训报告进行完整性检查（章节完整性、图表编号规范性）；
- 系统必须检查文档与代码的一致性（如报告中声明的功能是否在代码中有对应实现）；
- 分析结果必须以诊断报告形式呈现，每个问题标注具体章节、页码、问题类型；
- 系统应支持 Document Agent 进行文档结构与语义分析。

### 3.2.8 教师审核工作台（P0）

- 教师必须能够查看每位学生的 AI 分析诊断报告（代码 + 文档）；
- 教师必须能够逐条审核 AI 的诊断意见：确认（采纳）、驳回（填写驳回理由）、修改；
- 教师必须能够手动调整各维度评分及总分；
- 教师确认最终评分后，系统必须自动通知学生成绩已发布；
- 系统必须记录完整的审核日志（审核人、审核时间、审核操作明细）。

### 3.2.9 报表功能（P0-P1）

- 学生必须能够查看个人成绩单，包含总分、四维度评分明细、AI 诊断报告摘要，支持导出为 Excel；
- 教师必须能够查看班级成绩报表，包含成绩分布统计、完成率、各维度平均分、最高分/最低分，支持导出为 Excel；
- 教研负责人应能够查看全院教学报表（P1），包含跨班级对比、跨学期趋势分析。

# 4 非功能需求

## 4.1 性能指标

| 指标 | 要求 |
|---|---|
| 页面加载时间 | 首屏加载 ≤ 2 秒（P95），页面切换 ≤ 1 秒 |
| 接口响应时间 | 普通查询接口 ≤ 500 ms，报表生成 ≤ 5 秒 |
| AI 分析耗时 | 单次代码分析 ≤ 120 秒，单次文档分析 ≤ 60 秒 |
| 并发用户数 | 系统支持 200 用户同时在线，50 用户并发操作 |
| 数据存储容量 | 支持存储 10 万条以上实训记录 |

## 4.2 安全性需求

- 系统必须对用户密码进行加盐哈希存储（bcrypt 或 argon2），禁止明文或弱加密；
- 系统必须实现基于 RBAC 的权限控制，防止垂直越权（低权限角色访问高权限功能）与水平越权（同角色用户访问他人数据）；
- 系统必须对所有用户输入进行校验与过滤，防范 SQL 注入、XSS 跨站脚本攻击、CSRF 跨站请求伪造；
- 系统必须对敏感数据（如学生学号、联系方式）在日志与导出报表中支持脱敏处理；
- 系统必须采用 HTTPS 全链路加密传输；
- 系统必须记录关键操作日志（登录、评分修改、权限变更），支持审计追溯。

## 4.3 兼容性需求

- 浏览器兼容：必须支持 Chrome 90+、Edge 90+、Firefox 88+ 最新两个大版本；
- 分辨率适配：必须支持 1920×1080 及以上分辨率，应支持 1366×768 分辨率的基本可用性；
- 操作系统环境：服务端必须支持 Linux（Ubuntu 20.04+）部署，应支持容器化（Docker）部署。

## 4.4 易用性与可靠性需求

**易用性**：
- 核心操作路径不超过 3 步，如"实训提交"流程为：进入实训→选择提交方式→上传/填写地址→确认提交；
- 普通学生用户无需培训即可完成成果提交、查看成绩等核心操作；
- 所有表单必填项标红星，操作结果有明确反馈提示（成功/失败/进行中）；
- 操作失误支持撤销或返回上一步（如评分确认前支持回退修改）。

**可靠性**：
- 系统连续运行 72 小时无崩溃、无数据丢失；
- 故障恢复时间 ≤ 30 分钟；
- 部署环境负责数据库与对象存储的例行备份（非产品内功能）；
- AI 分析任务支持失败重试，单次分析超时时间为 5 分钟。

# 5 接口需求

## 5.1 用户界面规范

**整体风格**：采用浅色专业风格，卡片化信息布局；视觉定位为高校教务/LMS 类产品，对齐 **Campus Blue × Canvas / 腾讯教育** 配色体系。

**配色方案**（正式，详见《UI Design System》v1.1 §3）：
- **操作蓝 Primary** `#1677FF`：主按钮、链接、选中、进度、图表主线；
- **状态绿 Success** `#00B96B`：进行中、已通过、正向指标（不作主按钮）；
- **机构海军蓝** `#0B3A5C`：Logo 文字与稳重标题；
- **Canvas 红** `#E03C31`：仅 Logo 角标点缀，不大面积使用；
- **AI 紫** `#722ED1`：仅 AI 建议/置信度标识；
- 页面背景 `#F5F7FA`，卡片 `#FFFFFF`；
- 可交互预览：`docs/18-Color-Palette-Preview.html`。

**布局规范**：
- 顶部固定导航栏（胶囊菜单），包含系统 Logo、通知中心、用户头像与下拉菜单；
- 内容区采用卡片式布局组织信息，无强制左侧功能树（以顶部导航为主）；
- 表单/页面主操作使用 Primary 蓝；状态展示使用状态绿。

**交互规范**：
- 主操作使用 Primary 蓝；状态反馈使用状态绿 / 警告琥珀 / 危险红；
- 表单必填项标红星，校验失败在字段下方显示红色提示文字；
- 操作结果统一使用消息提示（成功 / 失败 / 警告语义色）；
- 数据加载中显示骨架屏或 Loading 动画，避免空白等待；
- 危险操作（删除、归档）须弹出二次确认对话框；
- AI 输出使用 AI 专属色标识，且不得直接作为最终成绩。

## 5.2 内部模块接口

系统采用前后端分离的 B/S 架构，前后端通过 RESTful HTTP 接口交互，数据传输格式为 JSON。后端内部模块通过服务间方法调用交互，核心交互关系如下：

- **实训模块与 AI 分析模块**：学生提交实训成果后，实训模块触发 AI 分析任务，分析完成后回调更新实训记录的 AI 诊断结果；
- **AI 分析模块与评分模块**：AI 分析模块输出诊断报告后，评分模块基于四维框架与自定义细则计算评分建议；
- **评分模块与报表模块**：教师确认评分后，评分数据同步至报表模块，驱动个人与班级报表数据更新；
- **用户模块与权限模块**：用户登录后，权限模块返回该角色可访问的功能菜单与接口权限列表，前端据此渲染 UI。

具体接口参数与数据格式详见《API 合约文档》。

## 5.3 外部第三方接口

- **AI 大模型服务接口**：对接 OpenAI API 或兼容接口，用于驱动 Code Agent、Document Agent 等 AI Agent 的代码分析与文档分析能力；调用方式为 HTTPS POST 请求，JSON 格式传参。
- **校园统一身份认证接口**（P1）：对接学校统一身份认证平台，实现学号/工号一键登录，同步用户基础信息；调用方式为 HTTPS POST/CAS 协议。
- **邮件/短信通知接口**（P1）：对接邮件服务（SMTP）或短信服务（阿里云短信），实现实训发布通知、成绩发布通知、截止时间提醒等消息推送；调用方式为 HTTPS POST 请求。

# 6 验收判定标准

## 6.1 功能项验收准则

- 需求文档中所有 P0 级功能必须 100% 可正常执行，操作结果与业务规则完全一致；
- 需求文档中所有 P1 级功能必须可正常执行，允许非核心交互细节存在微小差异；
- 每个功能的异常场景（如文件过大、网络中断、格式错误、逾期提交等）均有对应友好提示，无系统崩溃、数据丢失、数据错乱情况；
- 用户权限边界清晰，不存在越权操作、垂直越权、水平越权漏洞，不同角色登录后仅可访问各自权限范围内的功能与数据；
- AI 分析诊断报告的每个扣分项均有明确溯源标注（文件路径、行号/章节、问题类型），教师可逐条追溯复核。

## 6.2 非功能指标验收准则

- 性能指标测试结果全部满足第 4.1 节要求，首屏加载时间、接口响应时间、并发量、AI 分析耗时均达标；
- 兼容性测试覆盖 Chrome、Edge、Firefox 指定版本，页面无错位、功能无异常、样式一致性良好；
- 密码加密存储、RBAC 权限控制、SQL 注入/XSS/CSRF 防护、敏感数据脱敏等安全项全部符合第 4.2 节要求；
- 系统连续稳定运行 72 小时无崩溃；部署环境备份策略经验收确认。
