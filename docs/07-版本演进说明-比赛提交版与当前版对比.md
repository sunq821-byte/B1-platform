## 1 文档说明

### 1.1 编写目的

本文档梳理 **软件杯比赛提交版** 与 **当前开发版本** 之间的主要差异，便于团队在答辩、报告撰写、演示录制时准确描述项目演进路径，避免将比赛期内已交付能力与赛后迭代改进混淆。

### 1.2 版本基线定义

| 版本 | Git 基线 | 日期 | 说明 |

## 2 改进摘要（可直接用于答辩/报告）

相较 2026 年 7 月软件杯提交版，衡迹当前版本主要改进包括：

1. **UI 产品化**：三角色导航从 6/8/6 项精简为 3/5/4 项，TabHub 合并重复入口，统一 Campus Blue 视觉体系。
2. **AI 评价闭环**：落地试交 + 确认提交（方案 A），AI 参考分与教师终审分分离，四维度通用化，前后端评分映射统一。
3. **多专业覆盖**：从单一计科/Java Web 场景扩展为 **计科 + 经管 + 机械 + 校企** 四学院演示闭环，支持代码、报告、设计稿、企业交付物等多种成果形态。
4. **校企协同演示**：新增校企合作基地场景（`teacher4` 企业导师 + 实训学员），配套企业项目阶段交付任务与专属知识库/评分细则样例；企业独立角色（P1）在 Demo 阶段以师生账号模拟。
5. **真实联调**：移除 Mock，前后端全链路对接，仪表盘与报表接真实数据。
6. **演示能力增强**：四学院多状态种子数据 + `Material/` 分专业演示素材库，支撑答辩与录屏。
7. **文件与部署**：成果在线预览、MinIO 代理下载、上传稳定性与 Docker 部署问题修复。
8. **产品规则定稿**：一账号一角色、正式产品名「衡迹」、文档体系收敛至 PRD V2.4。

### 3.2 AI 评分与评价流程

| 维度 | 比赛提交版 | 当前版本 |
|------|-----------|----------|
| 数据模型 | 数据库迁移 V1–V5；`max_submit_count`；无独立试交表 | **V8 方案 A**：`submission_trial` 试交表 + `max_ai_analyze_count` + 确认提交字段 |
| 评分细则 | 7/9 完成 R/S/R/O 融合（比赛版已有基础） | 前后端完整打通；`GradingRuleForm` 建/编任务直接写细则 |
| AI 结果展示 | 基础 AI 分数面板 | `AIScorePanel` 强化 **「AI 参考分，非最终成绩」** 免责声明；试交时间线展示历次参考分 |
| 前后端映射 | 存在维度分数尺度不一致问题（7/9 曾修复 75/25 显示） | 新增 `aiDeductions.ts`、`teacherScoring.ts`、`submissionAIView.ts` 等工具，统一扣分项与教师终审分计算 |
| 四维度命名 | 偏计科 / 实验导向 | **V10 通用四维度**：完成度 / 规范性 / 质量 / 表达与完整性（适配全专业） |
| 教师复核 | 基础审核页 | 审核工作台优化：AI 参考分 vs 教师调整分对比；采纳 / 驳回 / 手动扣分逻辑更清晰 |

**演进要点**：从「AI 能打分」升级为「试交 → AI 参考分 → 确认提交 → 教师终审」的完整、可解释、可追溯闭环。

#### 核心业务规则（当前版定稿）

- 学生 **试交** 阶段：触发 AI 分析，消耗 AI 次数（默认 3 次，教师可配）。
- 试交成果 **教师不可见**，保护学生迭代空间。
- AI 输出为 **参考分**，界面明示非最终成绩。
- 学生 **确认提交** 后，成果进入教师审核队列且不可自行修改。
- 教师 **发布成绩** 为唯一正式成绩来源；驳回后 AI 次数重置。

### 3.3 多专业覆盖与校企协同（重点改进）

> **比赛版定位**：以计算机学院 Java Web 代码实训为主，演示数据集中在 **1 个班级、约 30 名学生**，成果形态以 **ZIP 源码包 + 实训报告** 为核心，评价维度命名偏计科/实验导向。
>
> **当前版定位**：面向 PRD 定义的「高校全专业实践教学场景」，通过 **同一套平台流程 + 任务级 R/S/R/O 评分细则 + 通用四维度框架**，覆盖理工、经管、工科设计、校企实训等多类型成果，证明平台与具体学科解耦。

**校企演示推荐路径：**

1. 使用 `teacher4` / `123456` 登录 → 审核工作台 → 审阅 `student12` 刘实训的企业阶段交付；
2. 查看 AI 诊断报告（完成度 / 规范性 / 质量 / 表达与完整性）；

**答辩表述建议：**

> 衡迹并非只做计算机实训——平台流程与评价配置与学科解耦，同一套「试交 + AI 辅助 + 教师复核」闭环可支撑计科代码、经管报告、机械设计、校企项目交付等多种场景。企业端在当前 Demo 中以校企基地师生账号模拟完整业务链路，独立企业角色 UI 为下一阶段 P1 工作。

## 6 答辩 / 报告引用建议

### 6.1 一句话版本

> 比赛版验证了「AI 辅助 + 三角色 + 评分细则」在计科场景的可行性；当前版在产品化方向上完成了 UI 精简、真实联调、试交确认闭环，并将演示场景扩展为 **计科 + 经管 + 机械 + 校企** 四学院多专业闭环，使系统从单一学科 Demo 演进为面向高校全专业实践教学的可展示、可答辩、可持续迭代的企业级平台雏形。

### 6.2 演示视频可强调的差异点

1. 登录后导航项数量明显减少，操作路径更短。
2. 学生试交页与 AI 结果页的「非最终成绩」提示。
3. 教师审核工作台的 AI 报告 + 人工复核交互。
4. 学情分析 / 数据报表中的 ECharts 图表与导出能力。
5. **多专业切换演示**：`teacher1` 代码实训 → `teacher2` 经管报告 → `teacher3` 机械设计 → `teacher4` 校企交付，展示同一平台适配不同成果形态。
6. **校企场景**：`teacher4` 审核 `student12` 企业项目阶段交付，强调导师复核与 AI 辅助并存。

### 6.3 常见追问应答

**Q：比赛版和现在的最大区别是什么？**

A：比赛版偏「功能验证 + Mock 演示」；当前版偏「产品化 + 真实联调 + 完整业务闭环」。最大可见差异是 UI 信息架构精简和试交确认流程的数据模型落地。

**Q：AI 评分改了什么？**

A：一是业务上明确 AI 参考分非最终成绩；二是技术上统一前后端扣分项映射与教师终审分计算；三是流程上落地试交次数管理与确认提交状态机。

**Q：为什么去掉 Mock？**

A：比赛期 Mock 便于前端独立开发；产品化阶段必须验证前后端契约、文件上传、AI 异步分析、报表统计等真实链路，Mock 无法覆盖这些集成问题。

**Q：系统是否只适用于计算机专业？**

A：不是。比赛版演示以 Java Web 代码实训为主；当前版已扩展至经管（PDF/Word 市场调研报告）、机械（设计说明书 + 图纸 ZIP）、校企（企业项目阶段交付）等场景。平台采用 **通用四维度 + 任务级 R/S/R/O 细则**，流程与具体学科解耦，教师按专业配置检查规则即可。

**Q：企业端做了吗？和企业是什么关系？**

A：PRD 已定义企业导师、企业培训管理员两种角色（P1）。当前 Demo 阶段在 **校企合作基地** 以 `teacher4`（王导师）和实训学员账号模拟企业导师复核流程，配套 `Material/07-知识库样例/校企/` 与企业交付素材。独立企业工作台 UI 为 P1 规划，核心业务链路（试交、AI 分析、导师复核、成绩发布）已与校内场景打通。
